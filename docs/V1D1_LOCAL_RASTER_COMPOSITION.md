# V1D-1 Production Local Raster Composition

## Purpose

V1C established exact dynamic restoration from the newest semantic model. V1D-0 then proved that the accepted Bitwig bitmap can receive prepared raster pixels through a direct, validated bulk write without changing transport ownership.

V1D-1 turns that selected research primitive into production source with locally generated byte frames.

It answers one bounded question:

> Can the accepted DrivenByMoss derivative expose a host-neutral, all-or-nothing opaque-BGRA region-write capability and exercise it through a complete local raster lifecycle while preserving V1C semantics, earlier diagnostic paths, one bitmap, and one USB writer?

It does not add an external process, shared memory, sequence/freshness, capture, scaling, or visual-source discovery.

## Accepted ownership chain

V1D-1 preserves this chain:

```text
newest retained ModelInfo
        -> complete current-semantic redraw
        -> current optional local raster request
        -> complete request validation
        -> absolute bulk row copies, or no write
        -> same logical IBitmap
        -> unchanged PushUsbDisplay
```

The historical composed output is not consulted. A rejected request does not need to restore old bytes because V1C has already rebuilt the current semantic frame before the writer runs.

## Host-neutral interface

```java
public interface IRasterWritableBitmap extends IBitmap
{
    boolean writeRasterRegion (
        RasterPixelFormat format,
        byte[] source,
        int sourceOffset,
        int sourceStride,
        int destinationX,
        int destinationY,
        int width,
        int height);
}
```

The first accepted format is:

```text
OPAQUE_BGRA8888
```

The interface has no host-specific type. It describes prepared raster bytes and destination geometry only.

### Success result

`true` means every declared destination pixel was written.

### Rejection result

`false` means no destination byte changed.

The boolean does not attempt to provide a diagnostic taxonomy. V1D-2 may collect counters or state outside the low-level sink without changing its all-or-nothing contract.

## Source-byte contract

The source array is caller-owned and exclusively stable until synchronous return.

```text
row 0           -> destination y
column 0        -> destination x
byte 0/pixel    -> blue
byte 1/pixel    -> green
byte 2/pixel    -> red
byte 3/pixel    -> alpha, required 0xFF
```

`sourceOffset` identifies the first source pixel. `sourceStride` identifies the byte distance between source rows and may be greater than `width * 4`. Padding is ignored.

The sink performs no:

- source crop from a larger image beyond offset/stride selection;
- scaling or resampling;
- interpolation;
- alpha blending;
- premultiplication conversion;
- color management;
- pixel-format conversion.

Those operations belong to a producer or adapter before the sink.

## Bitwig adapter ownership

`BitmapImpl` is the only accepted `IBitmap` implementation and the only class permitted to see the Bitwig `Bitmap`, `MemoryBlock`, and destination `ByteBuffer`.

Its raster responsibility is:

1. obtain one private destination memory view;
2. determine whether the destination layout is supported;
3. preserve ordinary `render()` and `encode()` behavior regardless of raster support;
4. validate every write completely;
5. bind and enforce the synchronous composition thread;
6. perform absolute bulk row writes;
7. expose only the host-neutral boolean method.

### Destination support checks

The generic adapter uses actual bitmap dimensions rather than Push constants.

Raster support requires:

- Bitwig `BitmapFormat.ARGB32`;
- four bytes per pixel;
- positive width and height;
- exact nonoverflowing byte count `width * height * 4`;
- memory block size equal to that count;
- writable direct view;
- position zero;
- limit and capacity equal to the expected count;
- accepted observed byte-layout assumptions.

Any failure marks the bitmap unsupported for raster writing. It must not make ordinary semantic rendering or encoding fail.

### Cached view

The selected model caches one destination view for the bitmap lifetime.

V1D-0 proved coherence across 1,920 sends, but Bitwig API 21 does not formally document view lifetime. V1D-1 therefore retains exact construction checks, fixture proof, and a fail-closed unsupported state. It does not expose or share the cached view.

`encode()` remains behaviorally unchanged rather than being rewritten to use the cached writer view.

### Record-to-class compatibility

The accepted source currently declares `BitmapImpl` as a public record. A record cannot add a private instance cache that is not a record component.

If V1D-1 converts it to a final class, the production change must preserve:

```text
public BitmapImpl(Bitmap)
Bitmap bitmap()
```

The preferred implementation also preserves record-equivalent `equals`, `hashCode`, and `toString` behavior. If it does not, the evidence must prove that no accepted source or supported integration relies on those semantics and explain why the change is still safe.

The conversion must not widen host exposure or alter render/encode behavior.

## Complete validation before mutation

Validation has two phases:

1. destination support, request metadata, ownership, and capacity;
2. complete source alpha validation.

No row is copied until both phases pass.

### Metadata checks

Reject:

- null or unsupported format;
- null source;
- width or height less than one;
- negative destination x or y;
- negative source offset;
- destination right/bottom overflow;
- destination outside actual bitmap bounds;
- packed row-byte overflow;
- source stride below packed row bytes;
- source last-row/end overflow;
- source too short;
- destination last-row/end overflow;
- destination view too short;
- unsupported destination layout;
- wrong thread after binding.

Use `long` arithmetic or exact overflow helpers so integer wrap cannot turn invalid metadata into a valid-looking offset.

### Alpha check

Every source alpha byte in every copied row must equal `0xFF`.

A nonopaque pixel rejects the complete request. The method must not copy earlier rows and then discover bad alpha later.

### Application

After validation:

```java
for each row:
    destination.put(destinationIndex, source, sourceIndex, rowBytes)
```

Use the absolute bulk overload. Destination position and limit remain unchanged.

### Thread binding

The first valid request may bind the writer to the current composition thread.

- malformed requests do not bind;
- first binding is race-safe;
- later wrong-thread calls reject before mutation;
- the accepted fixture thread was `Control Surface Session`;
- no queue, worker, executor, or asynchronous bitmap mutation is introduced.


## Local raster lifecycle

`DynamicLocalRasterPushFramePipeline` is package-private and one instance per display.

It owns only:

- fixed class-initialized generated arrays;
- primitive dimensions, offsets, strides, destinations, and state;
- one bounded state counter;
- optional bounded package-private observation accessors required by a temporary harness.

It retains no semantic bitmap, previous output, region snapshot, external frame, queue, task, or transport object.

### Required states

```text
SMALL
ODD_PADDED
MEDIUM
FULL
REPLACEMENT
NONE
STALE
INVALID
MALFORMED
```

Each state lasts a fixed documented number of eligible sends and the cycle wraps without growth.

### Generated patterns

Use project-generated patterns only:

- asymmetric corner markers;
- red, green, blue, white, and black bars;
- row and column markers;
- recognizable generated structure;
- opaque alpha;
- sentinel padding for the odd-stride case.

The patterns are generated or allocated only at class initialization, not per send.

### State behavior

Valid states invoke one `writeRasterRegion` call.

NONE, STALE, and INVALID invoke zero writer calls after V1C semantic redraw.

MALFORMED invokes one deliberately rejected call and must receive `false`; output remains semantic-only.

A target that is not `IRasterWritableBitmap` produces semantic-only output and no exception.

The pipeline returns the exact input `IBitmap` reference in every state.

No worker, queue, second bitmap, or asynchronous masking is permitted merely to reduce apparent wall-clock tails.

## V1D-2 boundary

V1D-1 ends with a synchronous local `byte[]` sink. It does not decide:

- shared-memory layout;
- producer buffer lifetime;
- zero-copy versus one bounded copy;
- sequence or timestamp rules;
- stale timeout;
- source identity and role;
- confidence or resolver metadata;
- helper restart protocol;
- capture permissions.

V1D-2 must choose those explicitly while adapting its current valid frame into the already-accepted V1D-1 sink.

External absence, crash, staleness, malformed input, permission denial, or resolver abstention must map to:

```text
current semantic redraw
        -> no raster write
        -> semantic-only output
```

## Result

When V1D-1 passes, the controller extension will possess the complete local consumer foundation required for real pixels:

```text
exact current semantics
        +
validated bulk raster sink
        +
all-or-nothing failure behavior
        +
one unchanged Push transport
```

Only then does an external latest-frame producer become the next uncertainty domain.
